# API Contract

> **Status: implemented for the mock backend.** The routes below are served by
> FastAPI under `/api/v1`. The `autopsy` simulator, graph, and agent pipeline is
> not wired yet; investigations are produced by a deterministic mock service.

## Conventions

- **Base path:** `/api`
- **Current version:** `/api/v1`
- **Legacy aliases:** `/api/health`, `/api/investigations`, `/api/scenarios`,
  `/api/scenarios/{scenario_id}`, `/api/scenarios/{scenario_id}/inject`,
  `/api/runs`, and `/api/subsystems` remain available for local development but
  are hidden from the OpenAPI document.
- **Media type:** `application/json; charset=utf-8`
- **Field naming:** `snake_case`
- **Timestamps:** UTC ISO 8601 with a `Z` suffix, for example
  `2026-10-30T12:00:00.000Z`
- **IDs:** opaque strings generated by the backend
- **Errors:** RFC 9457 `application/problem+json` for every failure
- **Pagination:** opaque cursor-based pagination on the investigation list
- **Authentication:** none in the current mock backend
- **Interactive docs:** `/docs`; OpenAPI document: `/openapi.json`

## Error responses

All errors use the same problem document. Validation failures add an `errors`
array. A `request_id` is also returned in the `X-Request-ID` response header.

```json
{
  "type": "https://mission-autopsy.local/problems/validation_error",
  "title": "Request validation failed",
  "status": 422,
  "detail": "One or more request fields are invalid.",
  "instance": "/api/v1/investigations",
  "code": "validation_error",
  "request_id": "7e6c2a2f9b8d4d8a9f0f0b5d3d1c2a10",
  "errors": [
    {
      "loc": ["body", "scenario_id"],
      "msg": "Field required",
      "type": "missing"
    }
  ]
}
```

| Status | `code`               | Meaning                                      |
| ------ | -------------------- | -------------------------------------------- |
| `400`  | `bad_request`        | The request cannot be processed as sent      |
| `400`  | `invalid_cursor`     | The pagination cursor is malformed           |
| `404`  | `not_found`          | The requested resource does not exist        |
| `405`  | `method_not_allowed` | The route does not support this HTTP method  |
| `422`  | `validation_error`   | Request body or query validation failed      |
| `500`  | `internal_error`     | An unexpected server error occurred          |
| `503`  | `service_unavailable`| A required service is not ready              |

## System

### `GET /api/v1/health`

Liveness and build metadata. No authentication, database read, or domain work.
The legacy `GET /api/health` alias returns the same body.

**Response `200 OK`**

```json
{
  "status": "ok",
  "service": "Mission Autopsy API",
  "version": "0.1.0",
  "environment": "development"
}
```

| Field         | Type   | Description                                      |
| ------------- | ------ | ------------------------------------------------ |
| `status`      | string | Always `ok` when the process is serving requests |
| `service`     | string | Configured application name                      |
| `version`     | string | Core package version, or the API fallback version |
| `environment` | string | `development`, `test`, or `production`           |

## Investigations

### `POST /api/v1/investigations`

Start an investigation from a scenario. The mock service completes immediately
and returns a deterministic summary. When the `autopsy` pipeline is integrated,
the same route will start the real workflow.

**Request body**

| Field         | Type              | Required | Constraints                       |
| ------------- | ----------------- | -------- | --------------------------------- |
| `scenario_id` | string            | yes      | 1–128 characters; not blank       |
| `title`       | string \| null    | no       | 1–512 characters                  |
| `description` | string \| null    | no       | Up to 4000 characters             |
| `fault_type`  | string \| null    | no       | 1–64 characters                   |
| `metadata`    | object            | no       | Request metadata; defaults to `{}` |

```json
{
  "scenario_id": "scn_power_undervoltage",
  "title": "Power bus undervoltage",
  "description": "Battery heater fault telemetry.",
  "fault_type": "power_degradation"
}
```

**Response `201 Created`**

```json
{
  "id": "inv_68ef911f11664a16888da495aafe4942",
  "investigation_id": "inv_68ef911f11664a16888da495aafe4942",
  "scenario_id": "scn_power_undervoltage",
  "title": "Power bus undervoltage",
  "description": "Battery heater fault telemetry.",
  "fault_type": "power_degradation",
  "status": "completed",
  "progress": 100,
  "current_stage": "completed",
  "error_message": null,
  "created_at": "2026-10-30T12:00:00.000Z",
  "updated_at": "2026-10-30T12:00:00.000Z",
  "completed_at": "2026-10-30T12:00:00.000Z"
}
```

`investigation_id` is an explicit alias of `id`. Status values are `pending`,
`running`, `completed`, `failed`, and `cancelled`. `progress` is `0`–`100`.

### `GET /api/v1/investigations/{investigation_id}`

Read status and summary metadata for one investigation. Returns `404` when the
ID does not exist.

**Response `200 OK`** — the same investigation object returned by `POST`.

### `GET /api/v1/investigations/{investigation_id}/hypotheses`

List ranked hypotheses, highest score first.

**Response `200 OK`**

```json
{
  "investigation_id": "inv_68ef911f11664a16888da495aafe4942",
  "hypotheses": [
    {
      "hypothesis_id": "hyp_aafe4942_01",
      "title": "Battery heater stuck on drained the power bus",
      "summary": "A failed heater switch kept the battery heater energized.",
      "causal_chain": [
        "Heater switch failed closed",
        "Battery heater stayed energized",
        "Battery state of charge fell",
        "Main bus voltage dropped below the safe limit"
      ],
      "evidence_ids": ["ev_aafe4942_01", "ev_aafe4942_02"],
      "contradiction_ids": [],
      "assumptions": ["Battery state of health was nominal before the fault"],
      "confidence": 0.82,
      "score": 0.79
    }

```

`confidence` and `score` are `0.0`–`1.0`. The mock returns three hypotheses.

### `GET /api/v1/investigations/{investigation_id}/timeline`

Read the reconstructed timeline in chronological order.

**Response `200 OK`**

```json
{
  "investigation_id": "inv_68ef911f11664a16888da495aafe4942",
  "events": [
    {
      "event_id": "evt_aafe4942_01",
      "timestamp": "2026-10-30T12:00:00.000Z",
      "subsystem": "command-and-data-handling",
      "event_type": "scenario_replay_started",
      "description": "Scenario replay began with the recorded mission inputs.",
      "severity": "info",
      "metadata": {
        "scenario_id": "scn_power_undervoltage"
      }
    }
  ]
}
```

`severity` is one of `info`, `low`, `medium`, `high`, or `critical`.

### `GET /api/v1/investigations/{investigation_id}/events`

Stream investigation progress with server-sent events (SSE). The response media
type is `text/event-stream`. The mock service emits the full lifecycle replay
immediately; set `MISSION_AUTOPSY_MOCK_STREAM_DELAY_SECONDS` to add a delay
between non-terminal events.

SSE fields:

- `id` — the progress percentage of the event
- `event` — `progress`, `complete`, or `error`
- `data` — JSON progress payload

```text
id: 0
event: progress
data: {"investigation_id":"inv_68ef911f11664a16888da495aafe4942","status":"running","stage":"queued","progress":0,"message":"Investigation accepted.","timestamp":"2026-10-30T12:00:00.000Z"}

id: 100
event: complete
data: {"investigation_id":"inv_68ef911f11664a16888da495aafe4942","status":"completed","stage":"completed","progress":100,"message":"Investigation complete.","timestamp":"2026-10-30T12:00:02.000Z"}
```

Returns `404` before the stream starts when the investigation does not exist.
Headers include `Cache-Control: no-cache` and `X-Accel-Buffering: no`.

### `POST /api/v1/scenarios/{scenario_id}/inject`

Validate a fault against a scenario and return an injection preview. This route
does not apply the fault or modify the scenario fixture; `preview` is always
`true` and `applied` is always `false`. Invalid faults return `400`; an unknown
scenario returns `404`; malformed bodies return `422`.

**Request body** — `FaultConfig`

| Field              | Type   | Required | Constraints                                            |
| ------------------ | ------ | -------- | ------------------------------------------------------ |
| `fault_type`       | enum   | yes      | Must be supported by the scenario                      |
| `target_subsystem` | string | yes      | Lowercase kebab-case; must be a valid option target     |
| `start_time`       | string | yes      | Aware UTC ISO 8601; fault must fit inside the mission   |
| `duration_seconds` | number | yes      | Greater than `0`; within the option's allowed range     |
| `magnitude`        | number | yes      | Non-negative; within the option's allowed range         |
| `parameters`       | object | no       | Fault-specific parameters; defaults to `{}`             |

Supported `fault_type` values are `power_loss`, `power_degradation`,
`thermal_overheat`, `sensor_drift`, `sensor_failure`, `communication_loss`,
`actuator_failure`, `software_fault`, and `unknown`. `unknown` is accepted by the
wire enum but is never a supported scenario option, so it fails validation.

```json
{
  "fault_type": "power_loss",
  "target_subsystem": "power",
  "start_time": "2026-10-30T12:01:00Z",
  "duration_seconds": 120,
  "magnitude": 40,
  "parameters": {"bus": "main"}
}
```

**Response `200 OK`**

```json
{
  "injection_id": "inj_2a863db8a9ce4f61b1f6c8b7f0c1d2e3",
  "scenario_id": "scn_power_undervoltage",
  "preview": true,
  "applied": false,
  "fault_config": {
    "fault_type": "power_loss",
    "target_subsystem": "power",
    "start_time": "2026-10-30T12:01:00.000Z",
    "duration_seconds": 120.0,
    "magnitude": 40.0,
    "parameters": {"bus": "main"}
  },
  "effective_start_time": "2026-10-30T12:01:00.000Z",
  "effective_end_time": "2026-10-30T12:03:00.000Z",
  "scenario": {"id": "scn_power_undervoltage", "...": "full ScenarioDetailResponse"}
}
```

`scenario` repeats the complete `GET /api/v1/scenarios/{scenario_id}` response;
it is abbreviated above for readability.

Injection-specific problem codes:

| Status | `code`                    | Meaning                                      |
| ------ | ------------------------- | -------------------------------------------- |
| `400`  | `invalid_fault_type`      | Scenario does not support this fault type    |
| `400`  | `invalid_fault_target`    | Target subsystem is not valid for this fault |
| `400`  | `invalid_fault_duration`  | Duration is outside the option's range       |
| `400`  | `invalid_fault_magnitude` | Magnitude is outside the option's range      |
| `400`  | `fault_outside_scenario`  | Fault window is outside the mission window   |

## Runs

### `POST /api/v1/runs`

Create an investigation run from a scenario plus an investigation configuration,
persist it as `queued`, enqueue it on the mock job queue, and return immediately
with `202 Accepted`. Scenario definitions and run configurations stay separate.

The canonical request nests all options under `investigation_config`. For
convenience, `fault_config`, `agent_config`, and `scoring_config` may be supplied
at the top level instead; mixing the nested and flat forms is rejected with
`422`.

**Request body**

| Field                  | Type              | Required | Notes                                         |
| ---------------------- | ----------------- | -------- | --------------------------------------------- |
| `scenario_id`          | string            | yes      | 1–128 characters; must exist                  |
| `investigation_config` | object            | no       | Canonical nested configuration                |
| `fault_config`         | object \| null    | no       | Flat form; validated against the scenario      |
| `agent_config`         | object \| null    | no       | Flat form                                     |
| `scoring_config`       | object \| null    | no       | Flat form; evidence/consistency/coverage sum to 1 |
| `title`                | string \| null    | no       | 1–512 characters; defaults from scenario name |
| `metadata`             | object            | no       | Caller metadata; defaults to `{}`             |

`investigation_config` fields:

| Field            | Type           | Default | Notes                                      |
| ---------------- | -------------- | ------- | ------------------------------------------ |
| `fault_config`   | object \| null | none    | If omitted, the mock selects the scenario's first fault option |
| `agent_config`   | object         | `{}`    | `enabled`, `max_hypotheses`, `temperature`, `model`, `seed`, `timeout_seconds`, `prompt_version` |
| `scoring_config` | object         | `{}`    | Weights default to `0.4`/`0.35`/`0.25` and must sum to `1.0` |

```json
{
  "scenario_id": "scn_power_undervoltage",
  "title": "Power bus undervoltage",
  "investigation_config": {
    "fault_config": {
      "fault_type": "power_loss",
      "target_subsystem": "power",
      "start_time": "2026-10-30T12:01:00Z",
      "duration_seconds": 120,
      "magnitude": 40
    },
    "agent_config": {"max_hypotheses": 3, "temperature": 0.0},
    "scoring_config": {
      "evidence_weight": 0.4,
      "consistency_weight": 0.35,
      "coverage_weight": 0.25
    }
  }
}
```

**Response `202 Accepted`**

```json
{
  "run_id": "run_08df4fd7d2834d92a9b87e9f7f1f2d3c",
  "scenario_id": "scn_power_undervoltage",
  "status": "queued",
  "title": "Power bus undervoltage",
  "investigation_config": {
    "fault_config": {
      "fault_type": "power_loss",
      "target_subsystem": "power",
      "start_time": "2026-10-30T12:01:00.000Z",
      "duration_seconds": 120.0,
      "magnitude": 40.0,
      "parameters": {}
    },
    "agent_config": {
      "enabled": true,
      "max_hypotheses": 3,
      "temperature": 0.0,
      "model": null,
      "seed": null,
      "timeout_seconds": 60.0,
      "prompt_version": null
    },
    "scoring_config": {
      "evidence_weight": 0.4,
      "consistency_weight": 0.35,
      "coverage_weight": 0.25,
      "contradiction_penalty": 0.2
    }
  },
  "fault_config": {
    "fault_type": "power_loss",
    "target_subsystem": "power",
    "start_time": "2026-10-30T12:01:00.000Z",
    "duration_seconds": 120.0,
    "magnitude": 40.0,
    "parameters": {}
  },
  "queue_position": 1,
  "created_at": "2026-10-30T15:00:00.000Z",
  "queued_at": "2026-10-30T15:00:00.000Z",
  "message": "Investigation queued."
}
```

`status` values are `queued`, `running`, `completed`, `failed`, and `cancelled`;
the mock returns `queued`. `fault_config` is repeated at the top level for
convenience and is identical to the validated object nested under
`investigation_config`.

Validation behavior:

- Unknown scenario → `404 not_found`.
- Unsupported fault type, target, duration, magnitude, or mission window → `400`
  with the same fault codes as `/inject`.
- Malformed body, unknown fields, mixed nested/flat configuration, invalid
  scoring weights, or invalid timestamps → `422 validation_error`.
- No simulation or agent work runs synchronously; `status` is `queued`.

## Mock service behavior

- The mock persists investigations and queued runs in SQLite and generates
  hypotheses and timeline events deterministically from the investigation ID.
- Scenario definitions are immutable in-process fixtures. Fault injection only
  validates and previews; it never writes back to a scenario.
- Runs are persisted with status `queued` and appended to an in-memory FIFO job
  queue. No simulator, graph, agent, or worker logic executes yet.
- It never imports simulator, graph, or agent code from `autopsy/`.
- Set `MISSION_AUTOPSY_USE_MOCK_SERVICES=true` (the default) to use it. The
  service factory is the single switch point for a future `autopsy` adapter.

## Frontend integration

- All HTTP calls live in `frontend/src/api/client.ts`.
- Wire types live in `frontend/src/types/api.ts` and mirror this document.
- Components receive data as props; they do not call the API directly.
- In development, Vite proxies `/api` to `VITE_API_PROXY_TARGET`.
- In production, `VITE_API_BASE_URL` points at the deployed backend.

## Change process

1. Update this document before changing a route or payload.
2. Update `backend/schemas/` and the route tests.
3. Update `frontend/src/types/api.ts` and the typed client.
4. Note breaking changes explicitly; do not silently change a field's meaning.
